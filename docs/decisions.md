# Design Decisions

이 문서는 NurPT를 공개 가능한 형태로 정리하면서 부딪힌 문제와 선택을 기록한 문서입니다. 코드의 세부 구현보다, 어떤 문제를 보고 어떤 기준으로 결정을 내렸는지 설명하는 데 목적이 있습니다.

## 1. PDF 표와 캡션은 완전 복원보다 검색 노이즈 감소를 우선했다

PDF 지침서는 표, 번호, 짧은 캡션, 페이지 조각이 섞여 추출되는 경우가 많았습니다. 표 구조를 완전히 복원하려고 하면 구현 범위가 커지고, 문서마다 예외가 달라지는 문제가 있었습니다.

그래서 `pdf_extract_check.py`에서는 페이지 단위로 원문 추출 결과를 보존하고, `pdf_chunk_json.py`에서는 RAG 검색에 방해되는 짧은 노이즈 라인과 세로로 깨진 조각을 줄이는 방향을 선택했습니다. 완벽한 문서 재현보다 검색 가능한 근거 조각을 안정적으로 만드는 것을 우선했습니다.

## 2. 청크는 페이지 경계를 넘기지 않고 1200자 기준으로 나눴다

RAG 답변에서 출처를 표시하려면 각 청크가 어느 문서의 몇 페이지에서 왔는지 유지되어야 했습니다. 그래서 청크를 만들 때 페이지를 넘겨 합치지 않고, 모든 청크에 문서명과 페이지 메타데이터를 남겼습니다.

기본 청크 크기는 `1200`자, overlap은 `80`자로 잡았습니다. 너무 짧으면 문맥이 부족하고, 너무 길면 검색 결과 안에 불필요한 내용이 섞일 수 있기 때문입니다. 문단 단위로 먼저 묶고 긴 문단만 나누어, 고정 길이 분할보다 문장 흐름을 최대한 유지하려고 했습니다.

## 3. LangChain 없이 작은 파이프라인을 직접 구성했다

처음부터 프레임워크를 크게 붙이면 빠르게 기능을 만들 수 있지만, 포트폴리오 공개본에서는 각 단계가 무엇을 하는지 드러나는 것이 더 중요하다고 판단했습니다.

그래서 PDF 추출, 청킹, 임베딩 색인, 검색, 프롬프트 생성, UI를 각각 작은 스크립트로 나눴습니다. 이 구조 덕분에 문제가 생겼을 때 어느 단계에서 확인해야 하는지 분리하기 쉽고, README에서 파이프라인 흐름을 설명하기도 쉬워졌습니다.

## 4. 벡터 검색만 쓰지 않고 키워드 보강 검색을 함께 사용했다

간호 지침서 질문에는 장치명, 처치명, 약품명처럼 짧고 중요한 단어가 자주 등장합니다. 순수 벡터 검색만 사용하면 질문 표현이 조금 달라졌을 때 원하는 문서가 뒤로 밀리는 경우가 있었습니다.

이를 보완하기 위해 문서 제목 가중치, 임상 용어 사전 기반 쿼리 확장, 카테고리/섹션/문서 단위 필터링을 추가했습니다. 예를 들어 장치명과 처치명이 함께 들어온 질문에서는 용어를 같은 뜻으로 섞어 설명하지 않도록 프롬프트 지침도 함께 넣었습니다.

## 5. smoke test는 정답 하나보다 실패 유형을 보는 방식으로 만들었다

RAG 품질은 단순히 답변이 자연스러운지만 보면 부족했습니다. 검색 결과가 엉뚱한 문서로 가거나, 출처가 불명확하거나, 근거 밖 내용을 일반론으로 길게 답하는 문제가 더 중요했습니다.

그래서 `rag_smoke_tests.md`에는 실제 현장에서 물어볼 법한 질문을 모아 두고, 좋은 결과와 주의할 결과를 함께 정의했습니다. 특히 "현장형 질문에 일반론만 길게 답한다"는 실패 유형을 기준으로 삼아, 답변이 검색된 근거 안에서 간결하게 나오도록 프롬프트와 출력 정리 로직을 조정했습니다.

## 남은 한계와 앞으로의 방향

현재 NurPT는 로컬 단일 사용자 환경에서 동작하는 프로토타입입니다. 실제 운영 환경으로 확장하려면 사용자별 권한 관리, 문서 접근 범위 분리, 질의 로그 비식별화, 검색 품질 평가 자동화가 필요합니다. 또한 PDF 표 구조를 더 정확히 보존하거나, 문서 업데이트 시 변경분만 재색인하는 기능도 개선 과제로 남아 있습니다.

이 프로젝트를 진행하면서 LLM을 단순히 호출하는 것보다, 문제에 맞게 문서를 구조화하고 검색 품질을 검증하는 과정이 중요하다는 것을 배웠습니다. SKALA에서는 이런 경험을 바탕으로 AI 서비스를 더 체계적으로 설계하고, 실제 사용자의 업무 흐름에 맞는 기능으로 발전시키는 역량을 키우고 싶습니다.
